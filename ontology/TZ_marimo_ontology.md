**Версія ТЗ:** 2.1 (узгоджено з `ontology/projects/ontology_UAV_models.json` v1.0)
**Гілка:** `ontology-project`, від `main`
**Мова коду та ідентифікаторів:** англійська. Предметні дані (домени, описи фасетів) — українська; поряд існує англомовна версія файлу й нотбука (§2.4).

**Зміни у 2.1:** класифікатор і онтологія рознесені на два незалежні пакети (§1.6); движок онтології більше не читає файли класифікатора (§1.5); додано англомовні версії даних і нотбука (§2.4); приймальні перевірки — `ontology/tests/check_ontology.py` (§6.7); ТЗ і перевірки лежать усередині пакета `ontology/`.

## 0. Контекст і мета

У репозиторії вже є референсна реалізація методу автоматизованої побудови **класифікаторів стратегій** ([П2], DOI 10.26906/SUNZ.2025.2.195-202): фасети з доменами → декартів добуток (FCE) → фільтрація обмеженнями (FCE\*).

Цей проєкт будує поряд **наступний шар** над тим самим апаратом — **онтологію моделей надійності**. Формат JSON походить від формату [П2] (`features` + `constraints`), розширений пошаровим кодуванням фасетів, новим типом правил і третім блоком `instances`, але є **окремим форматом** зі своїм движком: файли класифікатора онтологія не читає, а класифікатор не читає файли онтології (§1.5, §1.6).

Кінцева мета застосунку — три функції:

1. побудувати множину всіх **допустимих моделей** (валідних конфігурацій координат);
2. накласти на неї наявні **екземпляри** й отримати **матрицю прогалин** (gap-матрицю);
3. за заданими умовами місії знайти **найближчу наявну модель** і сформувати технічне завдання на нову.

Інтерфейс — нотбук [marimo](https://marimo.io/).

Стара наявна реалізація класифікатора: PyQt5 (`classifier/app.py`).

## 1. Жорсткі обмеження

**1.1. Логіку движка класифікатора не змінювати.** Движок перенесено з `models/classifier.py` у `classifier/engine.py` (§1.6) без змін у коді; його regression-базлайни (`classifier/TZ_classifier.md` §6) мають лишитися відтворюваними.

Новий функціонал — окремий пакет `ontology/` (движок `ontology/engine.py`). Якщо виникне спокуса відрефакторити спільну логіку в базовий клас — **не робити цього в цій гілці**; спершу закрити функціонал, рефакторинг окремим кроком з повторним прогоном таблиці вище.

**1.2. `app.py` (PyQt5) не видаляти і не змінювати по суті.** Він лишається робочим для файлів класифікаторів. Перенесено в `classifier/app.py`; єдина зміна — діалоги відкриття/збереження дивляться в `classifier/projects/` (шлях відносно модуля, а не робочого каталогу).

**1.3. Порядок елементів у JSON значущий** (успадковано з [П2]): порядок `features` фіксує порядок координат у всіх рядкових поданнях; порядок `constraints` визначає, яке правило «звинувачується» у блокуванні (діагностика за першою причиною). Не сортувати ні те, ні інше.

**1.4. Дедуплікацію не переносити.** У `classifier/engine.py` валідні конфігурації дедуплікуються за форматованим рядком, через що 48 комбінацій дають 42 рядки. Для gap-матриці потрібен **облік на рівні комбінацій**, а не рядків: gap-матриця рахує клітини простору, і злиття двох різних координатних векторів в один рядок зробить її хибною. Новий движок працює з векторами (кортежами/словниками), рядок формується лише для відображення.

**1.5. Сумісності з форматом [П2] у новому движку немає.** Онтологія не користується режимом `null` (див. §2.2), тому новий движок його не підтримує; так само не підтримуються `rule_type: "domain"`, дії з `allowed_values` і фасети без `id` (адресація за `name`). Такий файл **відхиляється при завантаженні** з `ValueError` і підказкою відкривати його пакетом `classifier`. У старому движку все це лишається: `project_swarm_of_UAV.json` використовує `mode: "null"`, і базлайн 144/42/96 на цьому тримається.

**1.6. Два незалежні пакети.** Класифікатор (`classifier/`, своє ТЗ — `classifier/TZ_classifier.md`) і онтологія не імпортують один одного й не читають файли одне одного. Склад пакета онтології:

```
ontology/
    engine.py               # Ontology, OntologyEngine (колишній models/ontology.py)
    notebook.py             # marimo, українська
    notebook_en.py          # marimo, англійська
    projects/               # ontology_UAV_models.json, ontology_UAV_models_en.json
    exports/                # вивід комірки експорту (у .gitignore)
    TZ_marimo_ontology.md   # це ТЗ
    tests/check_ontology.py # приймальні перевірки §6
```

Обидва каталоги — звичайні пакети з `__init__.py`; запуск — з кореня репозиторію (§6.1, §6.7). Спільного коду між пакетами немає і в цій гілці не з'являється (§7).

## 2. Вхідний файл

`ontology/projects/ontology_UAV_models.json` — передається разом із цим ТЗ. Структура:

```json
{ "meta": {...}, "features": [...], "constraints": [...], "instances": [...] }
```

### 2.1. Розширення блоку `features` порівняно з [П2]

| Поле | Значення | Призначення |
|---|---|---|
| `id` | `"O1"`…`"O9"`, `"M1"`, `"M2"` | **основний ключ адресації**; правила й екземпляри посилаються на `id`, а не на `name` |
| `layer` | `"O"` \| `"M"` | об'єктний шар (властивості системи) \| методологічний (рішення дослідника) |
| `facet_type` | `"структурний"` \| `"параметричний"` \| `null` | структурний змінює множину станів моделі, параметричний — лише інтенсивності переходів |
| `weight` | `2` \| `1` \| `0` | вага координати у зваженій відстані; для шару M завжди `0` |

Поля з [П2] (`name`, `description`, `type`, `domain`, `group`) зберігають свою семантику.

**Похідна величина D_max** описана в `meta.derived_quantities`. Це **не фасет**: вона обчислюється з умов місії та значення O6 (`одиночна` → `D_max = r + 1`; `множинна` → `D_max = n + r`) і задає межі домену O4. Движку вона потрібна лише для відображення підказок у нотбуці — на фільтрацію не впливає, бо домен O4 уже виражений відносно неї.

### 2.2. Розширення блоку `constraints`

**(а) `rule_type: "note"`** — анотація-наслідок. Конфігурацію **не блокує** і жодного домену не звужує; накопичує текст анотації для цієї конфігурації.

> Реалізувати за тим самим патерном, що й `null_overrides` у `classifier/engine.py` (патерн, а не спільний код — §1.6): накопичувати в окремому `annotation_overrides`, застосовувати **лише при формуванні виводу**, не записувати назад у `config`. Це пряме продовження виправлення з коміту `f42021a` — інакше анотація почне впливати на правила, що йдуть далі за списком.

**(б) `conditions[].values`** — складена умова належності: `{"feature": "O2", "values": ["0", "1"]}`. Істинна, якщо поточне значення належить переліку. Форма `{"feature": ..., "value": ...}` лишається як окремий випадок. Правило спрацьовує, коли **всі** умови в масиві істинні (кон'юнкція, як у [П2]). Використовується в c5 і c8.

**(в) `actions[].blocked_values`** у режимі `block` — перелік **вилучених** значень (у [П2] вказувалися дозволені). Це **єдина** форма дії `block` у новому движку: дія з `allowed_values` відхиляється при завантаженні (§1.5). Допустимі режими дій — `block` і `annotate`.

**(г) `constraints[].kind`** — довідкове поле (`семантичне` / `замикальне` / `міжшарове` / `узгоджувальне`). Движок його не інтерпретує; використовується в нотбуці для групування правил у звіті.

Режим `null` в онтології **не використовується**: незастосовність виражена значеннями домену (`"відсутні (m=0)"` для O4, `"відсутня"` для O8). Причина — координатний вектор має лишатися повним, інакше відстань між векторами не визначена.

### 2.3. Блок `instances`

```json
{
  "id": "i7", "model": "(n,rc,m)", "description": "...",
  "coords": {"O1": "...", ..., "M2": "..."},
  "status": "опубліковано | у рукописі | у розробці | gap",
  "refs": ["П4"], "role": "...", "origin": "...",
  "relations": [
    {"type": "є-спецвипадком", "target": "i3", "умови_звуження": "..."},
    {"type": "верифікується-звуженням", "target": "i1", "умови_звуження": "..."},
    {"type": "дзеркало-по", "facet": "O1", "target": "i4"}
  ]
}
```

`coords` містить значення **всіх** фасетів обох шарів; значення дослівно збігаються з елементами відповідного `domain`.

### 2.4. Англомовна версія

`ontology/projects/ontology_UAV_models_en.json` — повний переклад основного файлу: ті самі `id` фасетів, правил і екземплярів, той самий порядок масивів, ті самі ваги й та сама кількість значень у кожному домені (значення перекладені позиційно). Тому всі числа §6 для нього **ті самі**, і `ontology/tests/check_ontology.py` мусить проходити на обох файлах.

Мова файлу задається полем `meta.language`: `"uk"` (за замовчуванням, якщо поля немає) або `"en"`; інше значення — помилка завантаження. Керований словник, який движок інтерпретує, приймається в обох мовах незалежно від `meta.language`:

| Поле | Українською | Англійською |
|---|---|---|
| `facet_type` | `структурний` / `параметричний` | `structural` / `parametric` |
| `instances[].status` (реалізована модель) | `опубліковано` / `у рукописі` | `published` / `in manuscript` |
| `instances[].status` (прогалина) | `gap` | `gap` |
| `relations[].type` | `є-спецвипадком` / `верифікується-звуженням` / `дзеркало-по` | `is-special-case-of` / `verified-by-narrowing` / `mirror-along` |
| ключ умов звуження | `умови_звуження` | `narrowing_conditions` |

`meta.language` визначає лише мову тексту, який генерує сам движок: коментарі до суміжних прогалин, поле `origin` і опис нового екземпляра в Алгоритмі 1, тип відношення й ключ умов у плані верифікації. Поля `kind`, `group`, описи та значення доменів движок не інтерпретує, тож їхня мова довільна.

Нотбук має англомовний двійник `ontology/notebook_en.py` (§5).

## 3. Модуль `ontology/engine.py`

Публічний API (сигнатури орієнтовні, іменування на розсуд виконавця, але стабільне):

```python
class Ontology:
    @classmethod
    def load(cls, path: str) -> "Ontology": ...
    def facets(self, layer: str | None = None) -> list[Facet]: ...
    def facet(self, facet_id: str) -> Facet: ...

class OntologyEngine:
    def __init__(self, ontology: Ontology): ...
    def generate_object_space(self) -> list[dict]: ...
    def validate(self, coords: dict) -> ValidationResult: ...
    def valid_object_configurations(self) -> tuple[list[dict], list[BlockedEntry]]: ...
    def allowed_methodological_values(self, coords: dict) -> dict[str, list[str]]: ...
    def audit_instances(self) -> list[InstanceAuditEntry]: ...
    def gap_matrix(self, axis_x: str, axis_y: str, fixed: dict) -> GapMatrix: ...
    def distance(self, a: dict, b: dict, weighted: bool = False) -> int: ...
    def search(self, coords: dict) -> SearchResult: ...
```

### 3.1. `ValidationResult`

Щонайменше: `is_valid: bool`, `blocking_constraint: str | None` (id **першого** правила, що заблокувало — короткозамикання, як у [П2]), `annotations: list[str]`.

### 3.2. Пошарова генерація — ключова вимога

Декартів добуток будується **лише по шару O**. Значення шару M не перебираються: для кожного валідного O-вектора застосовуються міжшарові правила (c9, c10, c11), і результатом є **залишковий домен** кожного M-фасета.

Це реалізує в коді твердження з тексту роботи: шар M — фільтр і відомості про походження результату, а не вимір простору моделей. Якби M перебирався нарівні з O, кожна модель множилася б на кількість методів, якими її можна розв'язати, і gap-матриця втратила б сенс.

**Особливий випадок:** якщо для валідного O-вектора залишковий домен M1 або M2 порожній — це **суперечність у наборі правил**, а не властивість системи. Такий вектор потрапляє в окремий список `contradictory` зі списком правил, що спорожнили домен. Саме проти цього випадку існує правило c12; за поточним файлом список має бути **порожнім** (§6.2).

### 3.3. Відстані

Проста: кількість координат шару O, значення яких відрізняються.

Зважена: `d_w(a, b) = Σ_{k ∈ O} w_k · [a_k ≠ b_k]`, де `w_k` береться з поля `weight`.

Обидві **ігнорують шар M** (`weight = 0`).

## 4. Алгоритм 1 (функція `search`)

**Вхід:** вектор координат шару O, заданий умовами місії.
**Вихід:** або наявний придатний екземпляр, або новий екземпляр зі статусом `gap` разом із заготовкою технічного завдання.

1. **Перевірка допустимості.** Прогін вектора через усі правила. Якщо заблоковано — повернути id правила-винуватця та множину **найближчих допустимих векторів**, отриманих зміною однієї координати; завершити.
2. **Звуження шару M.** Обчислити залишкові домени M1, M2. Якщо якийсь порожній — повернути помилку суперечності (§3.2).
3. **Обчислення відстаней.** Для кожного екземпляра — `d` і `d_w` по шару O. Найближчий сусід `n* = argmin d_w`.
4. **Три виходи:** `d_w = 0` і статус ∈ {опубліковано, у рукописі} → повернути наявну модель; `d_w = 0` і статус = `gap` → приєднати до наявної прогалини; `d_w > 0` → створити новий екземпляр зі статусом `gap`.
5. **Заготовка ТЗ:** перелік розбіжних координат із типом кожного фасета (структурний / параметричний) — це оцінка вартості доробки; успадковані від `n*` відношення.
6. **Відношення «є-спецвипадком».** Брати з блоку `instances[].relations` вхідного файлу: у план верифікації нового екземпляра переносяться відношення типів `є-спецвипадком` / `верифікується-звуженням`, успадковані від найближчого сусіда `n*`, плюс усі екземпляри, що вже оголосили `n*` своїм узагальненням. Нових відношень движок **не виводить** — результат позначається як перелік **кандидатів**, а не як висновок.

   > **TODO — винесено на окреме узгодження, не реалізовувати самостійно.** Автоматично вивести «звуження» з координат неможливо: у доменах фасетів немає відношення порядку — з рядків `"1"` і `">1"` не випливає, що перше є спецвипадком другого, а `"необмежені (m≥D_max)"` не є ні звуженням, ні узагальненням `"обмежені (1<m<D_max)"` у сенсі включення множин. Потрібно окремо вирішити: (а) чи має «є-спецвипадком» формальний зміст у термінах координат, чи це змістовне твердження про вкладеність графів станів; (б) якщо має — чи задавати порядок спеціалізації явно (напр. `specialization_order` у JSON); (в) чи цей крок узагалі піддається автоматизації. Той самий TODO продубльовано в коді `ontology/engine.py` (`OntologyEngine.verification_candidates`).

7. **Рангування суміжних прогалин.** Відсортувати незаселені валідні клітини за зваженою відстанню d_w до нового екземпляра й повернути найближчі. Прогалини на d_w = 1 (розбіжність по параметричному фасету) успадковують структуру графа й закриваються перепризначенням міток; прогалини на d_w = 2 і більше вимагають перебудови простору станів. Якщо серед найближчих є дзеркало по O1, а призначення нового екземпляра — порівняння стратегій, воно позначається не як прогалина, а як передумова: без обох гілок порівняльний показник не обчислюється. Перелік справжніх дзеркал движок бере не з константи в коді, а з відношень `дзеркало-по` у блоці `instances` (i1↔i2, i3↔i4, i5↔i6) — тобто задається даними. Движок повертає повний відсортований список суміжних прогалин; скільки з них показати — параметр виклику (нотбук показує перші 10).

## 5. Нотбук `ontology/notebook.py`

Файл у пакеті `ontology/`; поряд — англомовний двійник `ontology/notebook_en.py` з тими самими комірками в тому самому порядку (за замовчуванням відкриває `ontology_UAV_models_en.json`). Будь-яку зміну комірок вносити в обидва файли. marimo зберігає нотбук як звичайний Python-модуль — не використовувати `.ipynb`. Нотбук сам додає корінь репозиторію до `sys.path`, тому запускається з будь-якого робочого каталогу.

Обов'язкові комірки:

1. **Завантаження.** `mo.ui.dropdown` по файлах `ontology/projects/*.json` (лише файли онтології — файли класифікатора сюди не потрапляють), відображення блоку `meta`.
2. **Фасети.** Таблиця: id, назва, домен, шар, група, тип фасета, вага.
3. **Обмеження.** Таблиця правил із розгорнутими умовами й діями, згрупована за полем `kind`.
4. **Прогін движка.** Кількості всіх / валідних / заблокованих / суперечливих; стовпчикова діаграма «скільки конфігурацій заблокувало кожне правило».
5. **Аудит екземплярів.** Для кожного i1…i7: координати в доменах / вектор валідний / залишковий домен M1 містить заявлений показник.
6. **Gap-матриця** — центральна комірка. Два `mo.ui.dropdown` для вибору осей (за замовчуванням `O2` × `O4`), решта фасетів — фільтри. Клітини трьох станів: **зайнято** (є екземпляр — показати id і статус), **прогалина** (валідна, порожня), **заборонено** (показати id правила).
7. **Пошук за місією.** Форма з `mo.ui.dropdown` на кожен фасет шару O → результат Алгоритму 1: таблиця сусідів з `d` і `d_w`, заготовка ТЗ, перелік симетричних прогалин.
8. **Експорт.** Кнопка збереження gap-списку в CSV і JSON (`ontology/exports/`, у `.gitignore`).

Застосунок має запускатися і як нотбук (`marimo edit ontology/notebook.py`), і як веб-додаток (`marimo run ontology/notebook.py`); так само для `notebook_en.py`.

## 7. Поза межами цієї гілки

- Рефакторинг `classifier/engine.py`, спільні базові класи чи спільний модуль для двох пакетів (§1.6).
- Будь-які зміни в `classifier/app.py` (крім шляху до `classifier/projects/`, §1.2) та у файлах `classifier/projects/project_swarm_of_UAV*.json`.
- Редактор обмежень в UI (правки JSON лишаються ручними).
- Розрахунок самих марковських моделей — це робота інструменту ASNA, застосунок лише формує технічне завдання.
- Обчислення D_max з конкретних n і r: у поточній версії домен O4 уже виражений відносно D_max, тому движку числові значення не потрібні. Якщо в нотбуці буде поле введення n і r — лише як довідкова підказка користувачеві.
