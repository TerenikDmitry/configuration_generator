**Пакет:** `classifier/`
**Джерело методу:** Terenyk & Kharchenko, «Automated development of classifiers: algorithms and software for generating strategies of deployment and reliability assurance for UAV swarm», Control, Navigation and Communication Systems, 2025, No. 2, DOI 10.26906/SUNZ.2025.2.195-202 — далі [П2].
**Статус:** референсна реалізація, логіка движка заморожена (§6). Документ фіксує, як движок і GUI працюють зараз і чому, — це контракт для будь-яких майбутніх змін.

## 0. Контекст і мета

Метод автоматизованої побудови **класифікаторів**: фасетно-ієрархічний опис ознак з обмеженими доменами → повний декартів добуток доменів (FCE) → послідовна фільтрація обмеженнями (FCE\*) до підмножини допустимих конфігурацій («стратегій»).

Робочий приклад зі статті — `projects/project_swarm_of_UAV.json` (6 ознак, 6 обмежень) — канонічний валідаційний випадок цього пакета. Якщо намір якогось рішення в `engine.py` неочевидний з коду, звірятися зі статтею.

Пакет незалежний від пакета `ontology/`: жоден не імпортує інший і не читає файли іншого. Спільного коду між ними не вводити.

## 2. Формат файлу проєкту

```json
{
  "features": [
    {"name": "...", "description": "...", "type": "enum", "domain": ["v1", "v2"], "group": "..."}
  ],
  "constraints": [
    {"id": "c0", "description": "...", "rule_type": "domain", "feature": "...", "allowed_values": ["..."]},
    {"id": "c1", "description": "...", "rule_type": "conditional",
     "conditions": [{"feature": "...", "value": "..."}],
     "actions": [{"feature": "...", "mode": "block", "allowed_values": ["..."]}]}
  ]
}
```

### 2.1. `features`

- `type` — `"enum"` або `"bool"`; `domain` — перелік допустимих значень (`[true, false]` для `bool`). Усі файли в `projects/` використовують лише `"enum"`.
- `group` — необов'язкова мітка для групування ознак; використовує GUI, движок ігнорує.
- Ознаки адресуються за `name`.
- **Порядок ознак у масиві значущий.** За [П2] ранніші ознаки — базовіші. Порядок фіксує `feature_sequence`, а через нього — порядок стовпців у рядку конфігурації (`/`-з'єднання в `_format_configuration()`), від якого залежить дедуплікація (§3.3). Переставляти ознаки лише з розумінням наслідків для порівняння виводу.

### 2.2. `constraints`

- `rule_type` — `"domain"` або `"conditional"`; інше значення — виняток.
- Правила застосовуються **у порядку масиву**, і порядок може змінити результат (наприклад, яке правило «звинувачується» у блокуванні). За [П2] порядок має відображати пріоритет правил.

### 2.3. Файли в `projects/`

| Файл | Зміст |
|---|---|
| `project_swarm_of_UAV.json` | канонічний приклад зі статті (українською) |
| `project_swarm_of_UAV_extensions.json` | канонічний + ознака `Наявність ремонту та обслуговування` (3 значення) і правило `c7` |
| `project_template.json` | мінімальний приклад; його розширювати для нових форм обмежень |

## 3. Движок `engine.py`

`ConfigurationGenerator` реалізує алгоритм [П2]: повний декартів добуток доменів (`calculate_all_configurations()`), потім фільтрація (`calculate_valid_configurations()`).

### 3.1. Семантика правил

- `rule_type: "domain"` — комбінація недопустима, якщо `config[feature]` не в `allowed_values`.
- `rule_type: "conditional"` — якщо **всі** умови з `conditions` збігаються з комбінацією, застосовуються **всі** дії:
  - `mode: "block"` — недопустима, якщо `config[feature]` не в `allowed_values` дії;
  - `mode: "null"` — записує `feature → 'None'` у словник `null_overrides` цієї комбінації; ніколи не блокує.

### 3.2. Інваріанти реалізації

- **`null_overrides` застосовується лише при формуванні виводу** (`{**config, **null_overrides}`) і не записується назад у `config`. Це виправлення з коміту `f42021a`: занулення на місці змушувало наступні правила бачити `'None'` замість справжнього значення, і дія правила залежала від його позиції відносно `null`-правила. Нові режими мусять явно вирішити, чи вони — трансформація відображення, чи справжня підстановка.
- **Правило-винуватець** зберігається в явній змінній `blocking_constraint` (коміт `f696ddb`), а не виводиться зі змінної циклу, тож комбінація записується як заблокована лише тоді, коли правило справді її відсікло.
- Повертається `(valid_configurations, blocked_configurations)`; кожна заблокована комбінація має id **першого** правила, що її відсікло (короткозамикання — діагностика за першою причиною, як у [П2]).
- **Дедуплікація** в обох методах іде через супутню множину `seen_*`, а не через `in list`; повертається список, тож порядок вставки зберігається. Не повертати перевірку членства в списку — цикл стане квадратичним на великих добутках.
- `statistics['iterations']` рахує перевірки умов і `domain`-правил, обнуляється на кожному виклику `calculate_valid_configurations()`. Перевірки дій `block` **не** враховуються — це міра роботи з умовами, а не всіх порівнянь.

### 3.3. Чому valid + blocked ≠ all

Це коректно. Для канонічного файлу стаття рахує 48 валідних **комбінацій**; движок друкує 42, бо список валідних дедуплікується за форматованим рядком, а правило `c1` (`mode: "null"`) зводить `Метод резервування` до `None`, коли `Резервування системи = БР`, — 12 комбінацій зливаються в 6 рядків (48 − 6 = 42).

Списки асиметричні навмисно: `valid_configurations` дедуплікований, `blocked_configurations` — ні (96 записів, але лише 78 різних рядків для канонічного файлу, бо заблоковані комбінації теж зануляються перед форматуванням). Якщо змінювати дедуплікацію чи обробку `null`, перевіряти також комбінаційний розподіл 48/96.

### 3.4. Розширення

Новий `rule_type` чи режим дії — розширити відповідну гілку в `calculate_valid_configurations()` і додати файл або правило, що його використовує (`project_template.json` — мінімальна основа). Базлайни §6 при цьому мають лишитися незмінними для наявних файлів.

## 4. GUI `app.py`

Один файл PyQt5, без окремих view/controller-модулів.

### 4.1. Вікно

`MainWindow` містить дві сторінки в `QStackedWidget`: побудова проєкту і (здебільшого не реалізований) перегляд класифікатора; перемикання — меню «Project» / «Classifier». Меню Project: Project View, Save Project, Load Project, Clear Project. Меню Classifier: Classifier View, Load Classifier. Діалоги файлів відкриваються в `classifier/projects/` (шлях відносно модуля).

### 4.2. Модель даних

`self.groups`: `{priority: {"group_name": str, "features": {priority: {"name": str, "description": str, "type": "enum", "options": [str, ...]}}}}`. Ключі `priority` — порядок вставки з 1; використовуються для відображення й для обміну при перетягуванні. `options` — плаский список кодів домену (напр. `["ПН", "ПП"]`), напряму відповідає `domain`. `type` завжди `"enum"`: шляху створити `"bool"` у GUI немає, і `'/'.join(...)` у `_format_configuration()` зламається на нерядковому значенні — не додавати `bool`, не виправивши це.

### 4.3. Редагування

- Перетягування (`DraggableLabel`, `handleDrop`) міняє місцями дві групи або дві ознаки однієї групи за їхніми ключами `priority`; перенумерації немає. Перетягування ознаки в іншу групу мовчки ігнорується. `DraggableLabel.mouseMoveEvent` повертається одразу після `drag.exec_()` і не має звертатися до `self`: обробник скидання перебудовує UI і видаляє цей QLabel.
- `AddFeatureDialog` збирає `name` + `description`; `AddOptionDialog` (кнопка «Add option +» біля ознаки) додає один `code` до `options`. Видалення чи редагування груп, ознак, значень немає — лише «Clear Project».

### 4.4. Серіалізація

`_serialize_project()` / `_deserialize_project()` — межа між вкладеним `self.groups` і плоским форматом §2; використовуються `save_project` / `load_project` / `load_classifier`.

- **Серіалізація:** обхід `self.groups` за пріоритетом групи, потім ознаки → один список `features` (кожна ознака отримує `"group": group_name`); `constraints` записується дослівно з `self.constraints`. Запис з `ensure_ascii=False, indent=4`, щоб українські файли лишалися читабельними.
- **Десеріалізація:** обхід `features` по порядку, нова група починається щоразу, коли `group` відрізняється від попередньої ознаки — **належність до групи визначається лише суміжністю**. Два несуміжні блоки з однаковим `group` після збереження → завантаження зіллються в одну групу. `self.constraints` береться з `data.get("constraints", [])` і далі GUI не змінюється (редактора обмежень немає).
- Перевірено на `projects/project_swarm_of_UAV.json`: `features` після циклу десеріалізація → серіалізація побайтно ідентичні, `ConfigurationGenerator` дає ті самі числа.

### 4.5. Відомі дефекти

- `refresh_classifier()` — заглушка і зламана: очищає `classifier_layout`, а потім викликає `add_group_block()`, який завжди вставляє в `self.project_layout`. Тому «Load Classifier» заповнює сторінку проєкту, а не класифікатора. Щоб будувати перегляд класифікатора, спершу дати `add_group_block()` цільовий layout (або окремий рендерер).
- `project_template.json`, правило `c1`: опис каже «If 'Feature 1' = 'domain 2', then 'Feature 2' != 'domain 5'», але дія націлена на `Feature 1` з `allowed_values` з домену Feature 2 — дія ніколи не виконується і просто блокує всі комбінації з `Feature 1 = domain 2`. Якщо робити шаблон справжнім прикладом — виправити `feature` на `"Feature 2"`, але числа §6 для шаблону зміняться.

## 6. Приймальні перевірки (регресія)

pytest-набору немає. Регресія — вивід CLI на трьох файлах; числа мають лишатися незмінними при будь-якій зміні пакета (виконувати **до** і **після** робіт):

```bash
python -m classifier.create_configurations classifier/projects/<файл>.json
```

| Файл | all | valid | blocked | iterations |
|---|---|---|---|---|
| `project_swarm_of_UAV.json` | 144 | 42 | 96 | 648 |
| `project_swarm_of_UAV_extensions.json` | 432 | 90 | 324 | 2088 |
| `project_template.json` | 9 | 3 | 6 | 15 |

Пояснення, чому valid + blocked ≠ all, — §3.3. Перенесення движка з `models/classifier.py` у `classifier/engine.py` перевірено: вивід CLI до й після збігається побайтно.
